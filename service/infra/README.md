# Infrastructure

Each directory under `environments/` is an independent Terraform root. Reusable, provider-specific
modules live in `modules/` and are referenced through repository-local paths. This pins each
reviewed environment configuration to the module implementation in the same commit.

The development root composes four repository-local modules. Every resource group is disabled by
default in `development.tfvars`; fill and validate its inputs before changing the corresponding
`enable_*` value. Module directories contain no development names, IDs or regions.

## Development workflow

Remote state belongs in the HCP Terraform workspace `your-say-news-development`. Supply its
organisation/workspace details through an ignored `*.backend.hcl` file when running
`terraform init`; do not commit tokens or local state.

For local validation without provider credentials or remote state:

```shell
cd environments/development
terraform init -backend=false
terraform fmt -check -recursive ../..
terraform validate
```

For an authenticated plan after the inputs and GitHub/provider secrets are ready:

```shell
cd environments/development
cp development.backend.hcl.example development.backend.hcl
terraform init -backend-config=development.backend.hcl
terraform plan -var-file=development.tfvars
```

Never run `apply` locally in the normal workflow. The reviewed saved plan is applied manually by
GitHub Actions. Commit the provider lock file generated by the approved Terraform version.

### GitHub Actions pipeline

`.github/workflows/infrastructure.yml` is the single infrastructure pipeline. It always runs format
and validation/test checks for infrastructure pull requests and pushes to every branch. Automatic
runs stop after those checks.

The pipeline's manual **Run workflow** form provides GitHub's branch selector and an environment
target:

- `infra_run_dev` works with any selected branch, connects to the development HCP workspace,
  creates the saved plan and then queues `infra_apply_dev` behind the
  `development-infrastructure` Environment approval gate;
- `infra_run_prod` rejects branches other than `main` and is a visible no-op placeholder until a
  production Terraform root, HCP workspace, credentials and protected apply Environment are
  approved.

The apply job uses only the binary plan produced earlier in the same workflow run. Configure
`development-infrastructure` to require manual approval before adding its secrets; otherwise
GitHub has no protection rule that can pause the job after planning. Development and production
manual runs use separate concurrency groups so neither environment will block the other.

Configure these GitHub Environment secrets when repository settings become available:

| Environment | Required secrets |
| --- | --- |
| `development` | `TF_API_TOKEN`, `AIVEN_TOKEN`, `HCLOUD_TOKEN` |
| `development-infrastructure` | `TF_API_TOKEN`, `AIVEN_TOKEN`, `HCLOUD_TOKEN` |

Add `CLOUDFLARE_API_TOKEN` and `GRAFANA_AUTH` to both Environments before their corresponding
resources are enabled. The HCP token is exposed to Terraform only as
`TF_TOKEN_app_terraform_io`. Saved plans are checksum-bound to the commit, lock file and backend
configuration, retained for one day, and rejected if they delete or replace a protected database,
bucket, DNS zone or VM.

## Supplying values

Environment-specific values belong only in the environment root:

```text
environments/development/variables.tf       declares the environment contract
environments/development/development.tfvars supplies non-secret development values
GitHub Environment secrets                  supply provider/runtime credentials
```

Never commit credentials, API tokens, generated passwords, tunnel tokens or private keys.

## Module conventions

All modules:

- have a narrow provider-specific responsibility;
- enable provider deletion or termination protection where available;
- add Terraform `prevent_destroy` to protected resources where appropriate;
- avoid provisioners for routine host and application deployment;
- leave provider configuration in the calling environment; and
- contain no environment-specific IDs, names, regions or credentials.

Keep these modules repository-local while Your Say News is their only consumer. Extract a stable
module to a versioned platform repository only when another application repository needs it.

### `linux-compose-host`

Owns the Hetzner VM, deny-public-ingress firewall, SSH-key references and deletion protection. It
does not deploy application images, render runtime secrets or open public API or SSH ports.

Inputs:

- `name`, `location`, `server_type` and `image`;
- existing Hetzner `ssh_key_names` for break-glass recovery;
- explicit `ipv4_enabled` cost decision;
- optional non-secret `cloud_init`; and
- shared low-cardinality `labels`.

Outputs are limited to server and firewall IDs, the server name and public addresses. The empty
Hetzner firewall denies new public inbound connections while allowing outbound traffic.

### `aiven-postgresql`

Owns the Aiven PostgreSQL service, application database, runtime and migration users, and deletion
protection.

Inputs:

- existing Aiven `project_name`;
- `service_name`;
- exact `plan` offered by Aiven and an optional `cloud_name` when the plan permits selecting one;
- application `database_name`; and
- runtime and migration `database_user_names`.

Aiven-generated passwords remain sensitive provider and state data and are not normal outputs.
For the Free tier, leave `cloud_name` null so Aiven assigns the provider and region; the assigned
identifier is then recorded as a non-secret output. Database grants belong to the audited migration
and release procedure. Outputs contain only the non-secret service endpoint, cloud, database name
and usernames.

### `r2-private-bucket`

Owns one protected private R2 bucket, its CORS configuration and lifecycle rules. The development
environment calls it separately for media and database backups.

Inputs:

- Cloudflare `account_id`;
- environment-specific `bucket_name`;
- immutable `jurisdiction` (`eu`) and best-effort `location`;
- `Standard` storage class;
- optional browser `cors_rules`; and
- optional provider-shaped `lifecycle_rules`.

R2 S3 access keys are runtime secrets and are not module inputs. Outputs contain only the bucket
name, jurisdiction and non-secret EU S3 endpoint.

### `cloudflare-api-tunnel`

Owns one remotely configured Cloudflare Tunnel and its proxied DNS routes. The development
environment supplies the public API route to `post-service:8082` and the private SSH route.

Inputs:

- Cloudflare `account_id` and `zone_id`;
- environment-specific `tunnel_name`; and
- a `routes` map from public hostname to origin service URL.

The module adds a final `http_status:404` catch-all. Cloudflare Access policies remain separate so
operator emails do not enter this module or Terraform state. The tunnel UUID and route hostnames
are non-secret outputs; the connector token is a sensitive output used only by the VM deployment
secret workflow.
