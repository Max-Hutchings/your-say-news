# ADR-029 — Versioned Post Unwrapped story lifecycle

Date: 2026-07-25

> **Amended by [ADR-035](ADR-035-2026-07-28-defer-unwrapped-prediction-stories.md):**
> prediction stories are removed for now. The active lifecycle generates observed stories only
> after the first safe vote milestone; human review, versioning and follow-up isolation remain.

> **Amended by [ADR-038](ADR-038-2026-08-03-cohort-causal-persuasive-narrative.md):**
> each option now presents one cohort-led, two-or-three-paragraph persuasive analysis of 50–100
> words rather than separate observed, context and synthesis sections. The admin proof must match
> the voter-facing article exactly.

> **Amended by [ADR-039](ADR-039-2026-08-03-admin-only-unwrapped-generation.md):**
> reaching a vote milestone no longer queues generation. Only an explicit administrator action may
> create reconciliation work or a provider-backed analysis job.

## Situation

After a canonical vote, users currently reach raw aggregate diagrams. MVP1 instead needs Post
Unwrapped: a concise, sourced case for every available option, followed by a second choice asking
whether the added context changes the user's view.

Observed demographic analysis is not credible for the earliest voters. Those users still need a
meaningful experience, so Pepper must produce an explicitly labelled prediction before the post
reaches 100 votes. Once sufficient votes exist, Post Unwrapped must transition to cached,
aggregate-backed stories without making voting wait for a model call.

The workflow must support binary and two-to-five-option multiple-choice posts, non-UK
jurisdictions, model/provider changes, human approval, durable regeneration and an isolated
follow-up response.

## Options considered

### 1. Generate a personalised story synchronously after every vote

This could respond to the individual voter and always use the latest result.

It would put provider latency and failure on the critical voting path, be expensive, fragment what
different users see and risk passing personal identity or characteristics to the model.

### 2. Generate only observed stories after a minimum milestone

Stories could be cached by milestone and remain aggregate-only.

This is safe after enough votes, but leaves the first voters without the promised experience or
encourages weak demographic claims from tiny samples.

### 3. Use approved prediction stories first, then approved observed stories by milestone

Generate one shared prediction from post context and external research before observed analysis is
available. At 100 votes and later milestones, generate new aggregate-backed drafts. Administrators
approve every story before it becomes eligible.

## Decision

Choose option 3.

### Page model

Post Unwrapped contains one argument page per immutable voting option, in option order, followed by
one reconsideration page:

- binary: two argument pages plus reconsideration — three pages;
- multiple choice: two to five argument pages plus reconsideration — three to six pages.

Every argument page gets approximately equal space and research attention. It contains a concise
headline, a prediction or observed cohort section, wider sourced context, a persuasive synthesis,
a caveat and accessible claim-level citations. Equal treatment does not require invented symmetry
when evidence for one option is weaker.

The reconsideration page is assembled by application code, not generated by the model. It uses the
same stable option IDs and label snapshots and asks:

> Has seeing the context for every option changed your view?

The user must select an option before continuing to the existing results diagrams. Selecting the
same option records that the context did not change their view.

### Prediction mode

Create a shared `PREDICTION` story from the immutable post question, options, explicit jurisdiction
and live external research. It contains no vote aggregate and must not imply that predicted cohorts
have already voted.

For a current canonical count at or below 100, deterministic application copy says:

> You are one of the first 100 voters. This is Pepper AI's prediction, not an analysis of the
> audience so far.

If the count passes 100 while the first observed draft awaits approval, the notice changes to say
Pepper's prediction remains while audience analysis is reviewed. It must not tell voter 101 that
they are among the first 100.

Prediction generation starts through durable background reconciliation after the post is
published. Publication is not blocked on model availability or administrator review in MVP1.
Until a prediction is approved, voters receive an honest `BUILDING` state and may continue to the
factual aggregate results. An unapproved prediction is never shown to voters.

### Observed mode and milestones

At 100 canonical votes, generate the first `OBSERVED` story from the versioned aggregate contract
defined in [ADR-028](ADR-028-2026-07-25-safe-demographic-insight-selection.md). Initial later
milestones are 250, 500 and 1,000, followed by a configurable growth rule.

Serve the newest approved eligible story. Continue serving the previous approved prediction or
observed story while a newer draft is generating or awaiting review.

Canonical voting durably marks the post for milestone reconciliation in the same database
transaction. A worker counts committed votes and inserts all newly crossed jobs with a unique
`(post, milestone, analysisVersion)` key. A periodic sweep recovers missed processing. Provider
failure can never roll back or reject a valid canonical vote.

Generation claims have a ten-minute lease. A periodic recovery task returns an expired claim to
the bounded retry queue, or marks it failed after the third attempt, so a worker crash cannot leave
a post permanently in `BUILDING`.

### Model-agnostic LangChain4j boundary

The Unwrapped application service depends on an `UnwrappedResearchGenerator` interface. A
LangChain4j adapter supplies the configured model and research capability and returns:

- typed story content;
- discovered/cited sources;
- configured model metadata; and
- a provider response ID.

Domain types, persistence and mobile contracts do not name Grok, xAI, OpenAI or a particular model.
A provider/model change replaces configuration or the adapter, not the Unwrapped domain contract.

Use one stateless generation invocation per story containing the ordered brief for every option.
The typed response must contain exactly one page for every supplied option. No second AI-verifier
call is included in MVP1.

The named LangChain4j `unwrapped` model is configured with server-side web search. That capability
belongs to the provider adapter; replacing the Responses-compatible adapter requires an equivalent
research tool and citation-metadata mapping.

### Research and citations

Prefer official statistics, government publications and original research. Each source is
classified as `OFFICIAL`, `ACADEMIC`, `REPUTABLE_MEDIA` or `OTHER`. When official evidence is not
available, the page must identify that limitation clearly.

Every factual claim has one or more source IDs. Central numeric claims require an official,
academic or otherwise high-quality source. URLs and model output are untrusted: validate HTTPS,
redirects, network targets, reachability, option IDs, claim/source references and bounded content
before a story can enter review.

Active source probes use a governed public-domain suffix allowlist and validate every redirect
target. The deployment may extend this list deliberately for additional jurisdictions and trusted
publishers. This trades some source coverage for a hard server-side SSRF boundary. Publisher type
is checked against governed official, academic and media domain categories; all-`OTHER` evidence
requires an explicit limitation on the page.

Pages remain concise. Full data-source references are always available from each page rather than
being hidden in a separate raw response.

The immutable research draft keeps one story-level source catalogue so validation and persistence
can deduplicate metadata and allow a source to support claims on more than one argument. The
voter-facing response resolves that catalogue into each argument page: every page contains only
the distinct sources cited by its claims, ordered by first citation. The public story object has no
separate source list, so a delivered argument is self-contained and cannot expose unrelated
sources.

### Review and immutable versions

Every generated prediction and observed story enters `DRAFT`. An administrator must explicitly
approve it before users can see it or reject it with an internal reason.

For MVP1 the existing Keycloak `admin` realm role is the dedicated site-administrator capability.
Every review endpoint enforces it server-side, then resolves the authenticated administrator to a
private local user ID for the audit record. This can be replaced by an application-owned
permission when administration becomes more granular.

Generated content is immutable. Review state and audit metadata may transition, but regeneration
creates a new story/analysis version. Persist the approving administrator privately with timestamps
and the approval/rejection event.

Stories retain:

- story, schema, analysis, aggregate, prompt and statistical rule versions;
- mode, post, milestone and canonical vote count;
- immutable option labels;
- structured pages and citations;
- model/provider response metadata;
- generation and review timestamps.

### Follow-up isolation

Store the reconsideration response separately from canonical votes with:

- private user and post IDs;
- story ID actually viewed;
- original canonical and follow-up option IDs; and
- timestamp.

Enforce one response per `(user, post)` across all story versions. The story ID preserves which
context the user saw, but a later milestone does not request another follow-up.

The response must never update canonical votes, aggregates, milestones or the story shown. It is not
published in MVP1 results.

### Client and API behaviour

`GET /posts/{postId}/unwrapped` is authenticated and requires the caller's canonical vote. It returns
only an approved story or an honest building/failure state. `POST
/posts/{postId}/unwrapped/{storyId}/follow-up` accepts only the new option ID and resolves the caller,
canonical choice and story server-side.

The mobile route renders known structured page types with dynamic progress from three to six pages.
It supports explicit Back/Next controls, reduced motion, screen-reader order and cited evidence.
After the required reconsideration response it opens the existing live aggregate diagrams.

## Reason

A cached, versioned story makes the experience fast, consistent and auditable while keeping external
generation off the vote path. Prediction mode gives early voters useful context without disguising
guesswork as audience evidence. The 100-vote transition creates a clear point at which deterministic
statistical selection may begin.

One page per option treats multiple-choice posts honestly instead of forcing them into a binary
support/opposition story. A single model-agnostic invocation keeps the first implementation simple,
and mandatory human review is the appropriate release control without a second model-verification
pass.

Separating the follow-up preserves canonical result integrity while still measuring whether context
changed a user's answer.

## Consequences and follow-up work

- Add explicit governed jurisdiction to post context, including a `GLOBAL` value.
- Add durable prediction/observed jobs, immutable story versions, citations, review metadata and
  follow-up persistence.
- Add administrator review endpoints and a protected review surface.
- Revisit the Keycloak `admin` role when application-owned administrative permissions are needed.
- Revisit the non-blocking publication rule if product policy later requires every first voter to
  have an approved prediction rather than an honest building state.
- Add exact story states for no approved prediction, generation failure, refresh awaiting review and
  insufficient observed evidence.
- Build binary, three-option and five-option contract/UI fixtures.
- Test that unapproved stories are never served and follow-ups cannot affect canonical aggregates.
- Preserve the stable option rules from
  [ADR-024](ADR-024-2026-07-21-binary-multiple-choice-voting.md).
- The detailed implementation plan is
  [Post Unwrapped agent architecture](../docs/plans/post-unwrapped-agent-architecture.md).
